The hub gateway, one shape, composed

This is the design for reaching microcontroller hardware from the BeamBots ecosystem through a small, recursive abstraction: the hub. A hub can read a sensor, drive an actuator, and route to child hubs — and because every hub is the same shape, they compose into a tree of any depth from one Raspberry Pi host down to a leaf on a wire. This v1 is deliberately small. It does four things well — a correct frame, a fail-passive floor, clock-free freshness, and a generated contract — and leaves the rest of the safety surface for later, marked where it is stubbed. 00Principles & what v1 covers

Read this first. The whole design is one idea — the hub — repeated, plus four pieces of discipline that keep a tree of hubs trustworthy. The point of v1 is to get communication flowing into BeamBots with a small, robust core; everything not on the v1 list below is deliberately deferred, and the document says so where it is stubbed.

The one goal

Reach a microcontroller from BeamBots through one composable abstraction — a hub that can sense, act, and route — so a robot of any shape is assembled by wiring hubs together, not by writing transport code.

Goals — what we optimise for

Stated as outcomes, not features — north-star targets the whole design pulls toward. Every decision below traces to one of these. (What v1 ships now versus what is deferred is the separate scope question answered later in this section; these goals describe the destination, not the v1 checklist.)

Compose, don't build

A new robot is assembled from existing hubs through the BeamBots topology and each hub's contract. You write core logic — a sample or a step — and the framework owns the plumbing.

Declare, don't wire by hand

You declare which hubs you want and how they connect. The framework owns the non-declarative work — moving commands and readings, checking the link follows through, deciding if a signal is fresh, surfacing an error.

Fail into legibility

A fault names itself — what broke, and where — and never collapses into ambiguous silence.

Safe in the gap

The robot reaches a safe state on any fault, independently of the part that failed, never depending on recovery succeeding.

Reason locally

You can understand and change one hub without holding the whole system in your head.

Test without hardware

Core logic is pure and replayable: develop on a laptop, reproduce a run from a log of values.

Right-rate, not max-rate

Move only the information that is needed, when it is needed. Never flood a wire or a CPU.

Evolve without rewrites

Add a hub, move it to another node, or swap a control law by editing data, not by rippling code.

Principles — how we think

  • 01 · One shape, composed. A hub is the only MCU node type — it senses, actuates, and routes to child hubs, in any combination. The root hub is the one that declares parent: :host: it talks to the host (the Elixir node) over UART and reaches its children over their links — a shared CAN bus, point-to-point UART, or a mix; every other hub hangs below it. Power comes from composing this one shape into a tree, not from many special node kinds.
  • 02 · Simple beats complete. v1 ships the smallest core that is still robust: a correct frame, a floor, freshness, a contract. We would rather ship four things that always work than twelve that mostly do. Deferred features are named, not hidden.
  • 03 · The router is meaning-blind. When a hub forwards a frame for a child, it moves bytes and never parses the payload. Only the producing hub and the final consumer read meaning.
  • 04 · A counter, not a clock. Freshness is "did seq advance?" — answered in the consumer's own beats, with no clock shared between boards. A producer's own t_dev rides along but is used only for same-device differences, never compared across nodes (§04).
  • 05 · Safe is the default; motion is earned. Nothing ever acts to become safe. An actuator hub drives to its safe action the instant its command goes silent, on its own chip — so it is safe even if its parent, or the host, is entirely gone (§05).
  • 06 · One source of truth for the wire. Frame layout, ids, and codecs are generated from one contract; a drift test fails the build if the C side and the Elixir side could disagree. Hand-edited byte math is the bug we are designing out (§06).
  • 07 · A hub is pure core plus a thin shell. What a hub computes — a sample (a sensor) or a step (a controller) — is a pure function you can test on a laptop. The framework owns the clock, the socket, and the routing.

Invariants — what must stay true

  • never  A value crosses the wire without a seq. A value re-presented as fresh though its seq never advanced is the failure the counter exists to catch.
  • never  A forwarding hub bumps a seq it is only relaying. Only the producing hub advances its own seq; a relay re-sends the same number, which no consumer trusts as new.
  • never  Freshness measured by comparing two boards' clocks. It is seq-advance within the reader's own fresh_for window — binary fresh or stale, no clock sync.
  • never  An actuator's safety depends on a frame arriving. The floor fires on command-seq silence; the broadcast e-stop is only a faster way to cause that silence.
  • always  Every actuator hub is born disarmed and every reader is born stale. A rebooted hub trusts nothing sitting in a buffer until it personally witnesses a fresh write.
  • always  The C constants and the Elixir definitions come from one generated contract. If a header on disk differs from the contract, the build fails — they cannot silently drift.
  • check  The CRC is a real, pinned CRC-16-CCITT. A parity-vector fixture asserts the exact same bytes hash on both sides; check(0x29B1) on "123456789" or the build fails.

01The hub — one recursive shape

Everything in the system is a hub. A hub is a node that can do any combination of three jobs, and one of those jobs is "be a parent to more hubs." That single recursive definition is the whole topology model.

sense

Read a device on its own pins — GPIO, I²C, SPI, ADC — sample the raw readings into a typed value, and publish it upward with a seq.

act

Receive a command value, drive a local actuator (PWM, a servo, a motor), and hold a floor that de-energises the moment the command goes silent.

route

Forward frames between its parent link and its child links, meaning-blind. A hub with children is a branch; a hub with none is a leaf.

A hub does any subset of these. A bare IMU on the end of a wire is a sense-only leaf. A wheel controller is an act-only leaf. A board on the robot's backbone that has an I²C sensor of its own and two child hubs hanging off it is sense+route. The host — the Raspberry Pi running Elixir and the BeamBots application — sits above the hub tree, not inside it; it is not a hub. The hub at the top of the MCU tree is the root hub: it is the hub that declares parent: :host, so it speaks serial (UART) upward to the host and bridges downward to its child hubs over their links — a shared CAN bus, a point-to-point UART, or a mix, each link's transport declared by the child it reaches. It is still an ordinary hub — it may read its own I²C sensor or drive its own actuator while it bridges — it is just the hub that owns the host connection.

why recursion is the whole abstraction

Because a hub can be a parent, you never need a separate "gateway type," a "leaf type," and a "router type" — those are just hubs with different jobs switched on. The root hub is simply the hub that declares parent: :host — the one that owns the host link; it is not a fourth kind. Adding a limb to the robot is adding a child hub. Moving a sensor deeper is re-parenting it. The tree can be shallow (root hub + a few CAN leaves) or deep (root hub → branch → limb → joint), and the host's view does not change: it names a node and a port on that node, and the framework finds the path. This is the single idea the rest of the document equips with a wire, a freshness rule, and a floor.

What a hub author writes

A hub author writes only the pure core for the jobs that hub does — a sample for a sensor, a step/safe-action for an actuator — plus a small contract (§06) declaring its ports and types. Placement also declares each hub's parent: and its uplink: transport (the root declares parent: :host), so the tree is stated by parent pointers. The framework supplies the scheduler, the link, the framing, the routing table, the floor, and the freshness monitor. Routing needs no per-hub author code at all: the route table is generated from the declared tree, so a hub routes because the topology says it has children below it.

03The wire — frame, COBS, and a real CRC-16

Above the wire, a value is a typed term keyed by (node, port). On the wire it is a flat, fixed-layout frame, COBS-framed with a CRC. The codec is the only place that knows the byte layout, and it is generated (§06) so the C and Elixir sides cannot diverge.

The identity is (NODE, PORT): which hub, and which endpoint on it (an IMU, a wheel). NODE is a flat, whole-tree-unique address — never a path, and a child link is not a port: ports name sense/act endpoints only, and a downstream hub is reached by addressing its own NODE, which the parent's route table maps to the specific link that reaches it. Routing is therefore a flat table lookup on NODE through the generated topology — route_table[node] → link — a branch hub forwards a frame onto the one link (of possibly several downlinks) that reaches that node, never a peer-name dispatch and never a port on the parent. Link indices are per-hub-local: each hub numbers its own links, with link 0 the up-link toward its parent (the host UART for the root) and its downlinks 1..N (a shared CAN bus is one link, each point-to-point UART its own). SEQ is the producing hub's own write counter, bumped by one on every real new value; a relay hub copies it verbatim. T_DEV is the producing hub's own 64-bit monotonic microseconds at the write — carried for same-device use only (§04), 64-bit so a hub's clock never wraps in the field; it is present only on ports that declare it (stamped ports), so a command or status frame omits it entirely. The decoder learns whether a frame carries it from the (NODE, PORT) it just read, so the optional field is never ambiguous. The CRC covers the whole decoded body (NODE…PAYLOAD), so it guards the routing header across every hop — the UART above the root hub and the CAN below it alike — not just the payload. The same frame rides both transports; the root hub re-frames it from one to the other without touching NODE, SEQ, T_DEV, or PAYLOAD.

the bug this fixes the old draft's CRC was not a CRC-16

The prototype computed :erlang.crc32(body) |> rem(65536) — the low 16 bits of CRC-32. That is a different function from CRC-16-CCITT, not a valid truncation of one. Either every frame fails to verify, or (worse) the C side was matched to the same wrong function and a weaker, non-standard check shipped silently — and a corrupted seq that slips through poisons the whole freshness story. v1 replaces it with a real, pinned CRC-16-CCITT and a fixture that proves both sides agree byte-for-byte.

ELIXIRplatform/wire/crc16.exCRC-16-CCITT-FALSE · pinned variant 
defmodule Wire.CRC16 do
  # CRC-16/CCITT-FALSE — the ONE variant, pinned so C and Elixir can't differ:
  #   poly 0x1021 · init 0xFFFF · NO input/output reflection · xorout 0x0000
  #   check value MUST be 0x29B1 over the ASCII bytes "123456789".
  import Bitwise

  def crc(bin), do: crc(bin, 0xFFFF)
  def crc("", acc), do: acc
  def crc(<<b, rest::binary>>, acc) do
    x = bxor(acc >>> 8, b) &&& 0xFF          # top byte XOR next input byte
    x = bxor(x, x >>> 4)
    acc = bxor(bxor(bxor(acc <<< 8, x <<< 12), x <<< 5), x) &&& 0xFFFF
    crc(rest, acc)
  end
end

On the UART (host↔root hub) the body+CRC is COBS-framed, delimited by 0x00 (COBS guarantees no 0x00 inside, so the delimiter is unambiguous). The host decodes inside a Circuits.UART.Framing module, so a corrupt or short frame is dropped before any value reaches the application — the framing layer counts it and moves on.

The framing module — where bytes become whole frames

The serial port hands up a stream of bytes that may split a frame across reads or glue two together. The framing module is the one place that turns that stream into whole, CRC-clean frames: it accumulates bytes, splits on the 0x00 delimiter, COBS-decodes each piece, checks the trailing CRC-16, and passes up only the bodies that survive. A bad CRC, a truncated COBS run, or noise is dropped and counted here — nothing above the seam ever sees a frame, only a verified body, so the codec (§06) never has to defend against garbage.

ELIXIRplatform/wire/framing_cobs.exthe Circuits.UART.Framing behaviour 
defmodule Wire.FramingCOBS do
  @behaviour Circuits.UART.Framing
  # COBS + CRC-16 framing for the host↔root-hub UART. CRC is verified HERE, so a
  # corrupt or short frame dies at the seam — the app only ever sees clean bodies.
  @delim 0x00

  @impl true
  def init(_args), do: {:ok, %{rx: ""}}    # rx = bytes seen so far but not yet a full frame

  # OUTBOUND: a full body+CRC in, a COBS-encoded delimited frame out.
  @impl true
  def add_framing(body, st) do
    frame = cobs_encode(body <> <<Wire.CRC16.crc(body)::16>>) <> <<@delim>>
    {:ok, frame, st}
  end

  # INBOUND: append new bytes, peel off every complete (delimited) frame, decode
  # + CRC-check each. Good bodies go up; bad ones are counted and dropped.
  @impl true
  def remove_framing(data, st) do
    {frames, rest} = split(st.rx <> data, [])
    bodies = for f <- frames, {:ok, body} <- [verify(f)], do: body
    in_frame = if rest == "", do: :ok, else: :in_frame   # tell Circuits.UART more may follow
    {in_frame, bodies, %{st | rx: rest}}
  end

  @impl true
  def frame_timeout(st), do: {:ok, [], %{st | rx: ""}}   # a stalled partial frame is discarded, not delivered
  @impl true
  def flush(_dir, st), do: %{st | rx: ""}

  # peel complete frames at each 0x00 delimiter; keep the trailing partial in rx
  defp split(buf, acc) do
    case :binary.split(buf, <<@delim>>) do
      [frame, rest] -> split(rest, [frame | acc])      # found a delimiter → one complete frame
      [partial]     -> {Enum.reverse(acc), partial}    # no delimiter yet → hold as partial
    end
  end

  # one frame: COBS-decode, then split body from its 2-byte CRC and check it.
  defp verify(""), do: :error                       # empty frame between two delimiters → ignore
  defp verify(frame) do
    with {:ok, decoded}              <- cobs_decode(frame),
         true                       <- byte_size(decoded) >= 2,
         <<body::binary-size(byte_size(decoded) - 2), crc::16>> = decoded,
         true                       <- crc == Wire.CRC16.crc(body) do
      {:ok, body}
    else
      _ -> Link.bump(:rx_drop) && :error    # bad CRC / truncated COBS / runt: count + drop, never deliver
    end
  end
end

# COBS: every 0x00 in the body is replaced by a pointer to the next 0x00, so the
# encoding is guaranteed null-free and 0x00 is an unambiguous frame delimiter.
# Overhead is ceil(n/254) bytes — bounded, the §05/03 promise. Pure, no I/O.

# ENCODE — emit each block prefixed by (len+1); a full 254-block uses code 0xFF.
def cobs_encode(data), do: enc(data, [], "")
defp enc("", blocks, cur), do: emit([cur | blocks])
defp enc(<<0, rest::binary>>, blocks, cur), do: enc(rest, [cur | blocks], "")
defp enc(<<b, rest::binary>>, blocks, cur) when byte_size(cur) == 253,
  do: enc(rest, [<<cur::binary, b>> | blocks], "")        # 254-byte block → 0xFF, no implicit zero
defp enc(<<b, rest::binary>>, blocks, cur), do: enc(rest, blocks, <<cur::binary, b>>)

defp emit(blocks) do
  blocks |> Enum.reverse()
  |> Enum.map_join(fn blk -> <<byte_size(blk) + 1, blk::binary>> end)
end

# DECODE — each code byte names a block length; insert 0x00 between blocks,
# except after a 0xFF (full) block. Returns :error on a truncated run.
def cobs_decode(data), do: dec(data, "", true)
defp dec("", acc, _first), do: {:ok, acc}
defp dec(<<code, rest::binary>>, acc, first) do
  n = code - 1
  case rest do
    <<blk::binary-size(n), tail::binary>> ->
      acc = if first, do: acc, else: acc <> <<0>>       # the zero this code stood in for
      dec(tail, acc <> blk, code == 0xFF)
    _ -> {:error, :truncated}                          # code points past the data → corrupt
  end
end
why the seam is the right home for the CRC garbage stops here

Putting COBS-decode and the CRC check inside the framing module means a corrupted frame never becomes a slot value — it is counted (rx_drop, crc_fail) and discarded at the lowest possible layer, exactly like Wire.decode drops an unknown port id (§07). This matters for the freshness story (§04): a corrupted seq that slipped through would be poison — it could fake an advance and re-present a frozen value as fresh — so the CRC must gate before anything reads seq. The encode/decode above is verified by a round-trip test over the edge cases (an embedded 0x00, a zero-run, the 254-byte block boundary, a real frame): every encoding is null-free and decodes back to the exact input, so the delimiter is never ambiguous. On the root hub's C side the same COBS+CRC lives in transport.c, and the parity vectors (§06) are the cross-language witness that both framings agree byte-for-byte.

the one transport detail the bridge must handle a frame is bigger than a classic CAN frame

The logical frame above (NODE…PAYLOAD, plus the 2-byte CRC) often exceeds a single classic-CAN data field (8 bytes). A controller with CAN FD and extended (29-bit) ids carries up to a 64-byte body in one frame; the ESP32's built-in TWAI is classic CAN (8-byte data field), so a wide body is split across several frames there. Either way the 29-bit id is generated from the contract as [NODE:8][PORT:8][rsv:13], so the controller filters on (NODE, PORT) in hardware (a node-wide or a port-wide mask both fall out of the layout) and the id range doubles as arbitration priority. CAN's own per-frame CRC guards each segment on one bus, but it cannot survive the re-framing at a branch hub (which decodes a frame and re-transmits it); so our end-to-end CRC-16 rides the body across CAN — as the body's 2-byte trailer — and is checked at every CAN receive, single- and multi-frame alike, exactly as at the UART seam.

Frame size is therefore a real constraint, not an afterthought. A value type whose body exceeds the single-frame limit of the available controller is segmented by the bridge into ordered fragments — one per CAN frame, body bytes only — and reassembled before the CRC check, so the CRC is over the whole reassembled body, never per-fragment. The fragment index, a first/last marker, and the low bits of the body's seq ride the reserved id bits (below), never the data field, so the CAN body bytes are byte-identical to the UART body and the parity vectors (§06) hold across both transports. The t_dev field is per-port (§04), which keeps command and status frames inside one classic-CAN frame; a build check (§06) computes header + payload per value type and refuses a contract whose body overruns the segmentation ceiling (64 fragments → 512 bytes) or, on a one-frame transport, the single-frame size (this per-frame size check is distinct from the link-bandwidth wire-budget of §04/§06, which is SAFeD). Two facts make this matter in practice: the largest field is the 8-byte t_dev, and the canonical sensor types are wide — a full IMU value (a quaternion plus two vectors) is a 40-byte payload, a 54-byte wire body: one CAN FD frame, or seven classic-CAN fragments. A bridge never truncates an oversized body — reassembly is fail-closed (a gap, reorder, or stray fragment drops the whole body and is counted, never delivered partial), and the one body that genuinely cannot be sent — one over the 512-byte ceiling, which the build check forbids — is refused and counted (tx_oversize), because a truncated body is silent corruption that would poison decode and the freshness counter (§04).

PORT · 8bwhich endpoint on that hub

8 bits of NODE = 254 addressable hubs (0x00 reserved for broadcast; the host is logical id 0, above the tree); 8 bits of PORT = 255 endpoints per hub — both well beyond any single-tree v1 bot. The low 13 bits carry the segmentation header: a 6-bit fragment index (≤ 64 fragments, a hard 512-byte body ceiling), a FIRST bit on index 0 (the only fragment that may seed a reassembly buffer — a stray fragment never starts one), a LAST bit on the final fragment (triggers the CRC check), and the body seq's low 5 bits binding every fragment to its body (so a lost fragment can never splice the next body into a stalled buffer). A single-frame body sets FIRST and LAST with index 0. The fragment bits sit below NODE/PORT, so they never disturb the (NODE, PORT) hardware filter and never outrank arbitration priority — NODE 0x00 still wins the bus. Because the id is generated, "this class of frame outranks that one" is decided by id-range allocation in the contract — declarative, not a hand-written scheduler.

the e-stop wins the bus, physically lower id wins arbitration

CAN arbitration is won by the lowest id, and the broadcast disarm is NODE 0x00 — the lowest id on the bus. So the e-stop does not merely get sent promptly; it beats every contending data frame onto the wire at the same instant. This sharpens §05's "accelerator, not mechanism": the stop that causes command-silence reaches the actuators as fast as the physical layer allows, while the floor still backstops if the bus is cut entirely. The accelerator's speed is now a property of the id space, not of hope — and the end-to-end CRC-16 still guards the body across the re-framing boundary exactly as above, since the id shape changes only how a frame is addressed, never what its body carries.

04Freshness — seq, fresh_for, and born-stale

A transparent router has one hazard a directly-wired sensor never had: at the consumer, no message is ambiguous between "nothing changed" and "the hub went silent." The fix is to make trust a counter, not a clock. This is what makes the meaning-blind router safe to rely on.

Two stamps, two jobs — only one is in the trust path

seq — "is it still flowing?"

A counter the producing hub bumps by one on every real new value. A consumer remembers the last seq it saw; if it advanced within its fresh_for window, the value is fresh, else stale. No clock comparison, survives lost frames (seq just jumps) and counter wrap (the test is "advanced?", not "by how much"). This is the only stamp the freshness check reads.

t_dev — same-device only, per-port

The producing hub's own monotonic µs at the write. Never compared across nodes; never read by the freshness check. It exists for same-device math: aligning samples from the same device in fusion, measuring a single hub's jitter, replaying a recorded run against its own in-band clock. It is opt-in per port in the contract, because at 8 bytes it is the largest field — a port that needs it carries it (sensors that feed fusion/replay); a command or status port, which never uses it, omits it and stays small (it would otherwise be half the frame). On a port that carries it, the gate cost is still zero.

why both, and why the split is strict

The two stamps are kept rigidly apart. The instant t_dev leaks into the freshness decision, a shared-clock problem is re-introduced across (potentially) three boards in the tree — exactly the bug-class clock-free freshness exists to avoid. So: seq decides trust; t_dev is a passenger for same-device math, carried only on the ports that need it. One field, one job, each.

The relay rule — verbatim and in order

A routing hub forwarding a child's frame copies seq and t_dev verbatim — it must never mint a new seq. Re-sending the same seq is a re-arrival, which no monitor counts as a new write. If a relay could bump seq, it could manufacture a false "fresh" for a value the producing hub never updated — the precise failure the counter prevents.

v1's relay carries a second, equally load-bearing discipline: it is a strict FIFO byte pump. It forwards frames in arrival order, re-framing for the destination transport and re-CRCing the same body, and it never reorders, holds, batches, or dedupes. This matters because the freshness test below — and the floor in §05 — defines "seq advanced" as a plain inequality (seq != last_seq), which is sound only while every path to a consumer is in-order. Point-to-point UART and CAN are in-order by nature; the relay is the one component that could break that, so v1 forbids it from doing so. (When conflation is added later it may drop superseded frames per (node, port), advancing seq only if the value itself changed — but it must preserve per-(node,port) order, or the inequality test must simultaneously become a windowed forward compare; both are SAFeD.)

The window and born-stale

Each consumer declares a fresh_for window as a multiple of the producer's nominal period, so "a window shorter than one write" cannot be expressed. A freshly started or restarted consumer has witnessed nothing, so it is born stale: it distrusts whatever value is sitting in the registry until it personally sees seq advance since its own boot. This is what makes a restart safe — a rebooted board never trusts a leftover reading.

"Advance since its own boot" is resolved strictly, because on its very first observation a consumer cannot tell a value left in the slot before it booted from the producer's first value after it booted — both are just "the first seq I have seen." So the first observed seq only records a baseline; the consumer becomes fresh only when it sees the seq change from that baseline. A leftover value is therefore never trusted, at the cost of up to one extra producer period of first-trust latency after boot. This is the conservative reading, and the safe one. (A boot-epoch / generation marker that lets a consumer distinguish the two cases on first sight — and so trust a genuine post-boot first value immediately — is a possible later elaboration; SAFeD, since it only ever removes latency, never adds trust.)

ELIXIRplatform/monitor.exone comparison per port, per beat 
# On each local beat: did this port's seq advance within fresh_for beats?
# `witnessed` starts false → born stale. STRICT: the first seq seen is only a
# baseline; trust begins on the first CHANGE from it, so a value left in the slot
# before this consumer booted is never trusted (see "born-stale", above).
def check(state, port) do
  {_value, seq_now, _t_dev} = Registry.get(state.node, port)
  advanced? = seq_now != nil and state.last_seq != nil and seq_now != state.last_seq
                                                          # inequality: sound under in-order links (§04 relay)
  witnessed = state.witnessed or advanced?                # flips true on the first real advance
  idle   = if advanced?, do: 0, else: state.idle + 1
  fresh? = witnessed and idle <= state.fresh_for           # a counter, no clock
  %{state | last_seq: seq_now, idle: idle, witnessed: witnessed,
            status: if(fresh?, do: :fresh, else: :stale)}
end

In v1 a stale critical input means the control law returns "no command" (so it stops writing :motor_target, whose seq then freezes), and downstream the actuator hub's own floor (§05) sees its command go silent and de-energises. Two independent checks, each firing on a producer going quiet — exactly what a meaning-blind router can support, because neither check ever needs the router to understand the payload.

Different sensors at different rates — it falls out of this, for free

A real robot mixes rates constantly: an IMU at 1 kHz, a range sensor at 20 Hz, a battery gauge at 1 Hz, a 50 Hz control loop reading all of them. The design needs no rate-matching machinery for this, because three choices already made it a non-problem.

Rate is per port, not global

Each port declares its own rate in its contract. The IMU port says 1 kHz, the range port says 20 Hz — two independent facts about two devices. There is no system tick everyone must share, so adding a fast sensor next to a slow one is just two contract entries.

Every port is its own box

Each (node, port) is its own overwrite-only registry row. A 1 kHz producer overwriting its own row cannot touch — or drown — a 20 Hz producer's row. There is no shared queue for a fast stream to flood, so rates never interfere.

Consumers pull on their own beat

A reader samples the latest value of each input on its beat, decoupled from every producer's rate. The 50 Hz loop reads the newest pose and the newest range each tick and does not care that one updated 20× more often — it just takes what is in each box now.

So the rule is simply: producers write as fast as their hardware and contract allow; consumers read the latest on their own beat; freshness is judged per input against that input's own rate. The IMU writing 1 kHz means its seq climbs fast and its fresh_for window (a multiple of a 1 ms period) is tight; the range sensor's seq climbs slowly and its window (a multiple of a 50 ms period) is wide — and the same monitor code (above) checks both correctly, because the window is always expressed in the producer's periods, never in wall-clock time. A 50 Hz loop can read a 1 kHz input and a 1 Hz input side by side and get an honest fresh/stale answer for each.

where rate does need attention bandwidth and time-alignment

Two places rate is not free. (1) Wire bandwidth. Many ports streaming on one link must fit the wire: the budget is Σ(port rate × frame size) against the link's baud, and a topology that over-subscribes the busiest wire should be refused at boot. Bursty push traffic is bounded by conflation — one pending value per (node, port), newest wins — so a vibrating sensor that fires faster than its nominal rate still costs only its drain rate on the wire. Both the wire-budget check and conflation are SAFeD in v1; until then, keep declared rates conservative and the tree shallow. (2) Time-aligning two different-rate streams. "Newest of each" describes slightly different instants when the robot is moving fast — fusing a 1 kHz IMU with a 20 Hz range to estimate one pose needs the samples aligned in time. That is the one job the per-value t_dev (§04, same-device only) exists for: predict on the fast input each time its seq advances, correct on the slow input when its seq advances, and use t_dev differences to line them up. Fusion itself is SAFeD; the field it will need is already on the wire.

05The floor — fail-passive & born-disarmed

This is the safety core, and it is small on purpose. A router puts a parent hub in the command path of everything below it, so the safe state cannot live on the parent: it lives on each actuator hub's own chip, fires on command silence, and needs no frame to arrive. The heartbeat and the broadcast e-stop are kept — but as a faster way to cause silence, never as the guarantee.

The floor — the guarantee

An actuator hub watches the seq of its own command against a compiled-in window, on its own monotonic clock. If the seq stops advancing for the window, it drives the plant to its safe action — a value of the command port's own value-type (zero torque for an effort port, a neutral position plus brake for a servo) — and latches disarmed. The floor is value-type-agnostic: it holds two opaque packed values (the commanded one and the safe one) and swaps between them on the seq, never interpreting their bytes — it does not know a torque from a position. Because this runs on the actuator's chip and needs no inbound frame, it fires even if the parent hub, the whole tree above it, or the host is entirely gone.

Born-disarmed — motion is earned

Every actuator hub boots armed = false with its output already at the safe action. It only begins driving after it witnesses a fresh, in-window command seq advancing since its own boot. A reboot, a power glitch, a stale frame left in a buffer — none of these can energise it. Motion is something the hub continuously earns, never a default it falls into.

the e-stop is an accelerator, not the mechanism

v1 keeps your heartbeat and broadcast disarm — but wired so they share one tested code path with the floor. The host sends a periodic heartbeat; a hub's parent refreshes its command stream as long as the host is alive. A broadcast disarm (or a missed heartbeat, or a pulled wire, or a dead parent) all resolve to the same thing at the actuator: its command seq stops advancing → the floor fires. So there is no second "react to the e-stop frame" path that could itself fail; the e-stop just makes the silence happen faster than waiting for the window. The one path — "my command went silent" — covers parent-death, bus-cut, and deliberate stop.

/* The floor lives on THIS chip. The window is compiled in from the contract.

void on_command(const Frame *c) {   /* a command frame for this hub's actuator port */
  memcpy(target, c->payload, SAFE_N);  /* opaque packed bytes — the floor never decodes them */
  cmd_seq = c->seq;                  /* watch the seq, not the value */
}

void control_tick(void) {            /* the ~kHz drive loop */
  uint32_t now = millis();
  /* "Advanced?" is a plain inequality: ANY change in seq is a new command.
     SOUND ONLY because every path to this chip is in-order — point-to-point
     UART/CAN preserve order and the relay is a strict FIFO byte pump (§04), so
     'seq differs' == 'seq is newer'. No magnitude test ⇒ the wire's u16 seq read
     into u32 is harmless and counter wrap is a non-issue (we never ask by how much). */
  if (cmd_seq != last_seq) { last_seq = cmd_seq; last_advance_ms = now; }  /* fresh */

  bool fresh = (now - last_advance_ms) < FLOOR_MISSES * CMD_PERIOD_MS;
  if (!fresh) { armed = false; drive(SAFE_ACTION); return; }   /* silence → safe, latched */

  if (!armed && fresh) armed = true;     /* earn motion: a fresh, in-window command */
  drive(armed ? target : SAFE_ACTION);                          /* default is always safe */
}
deliberately deferred what v1's floor does not do yet SAFeD

v1's re-arm is just "a fresh command resumes motion." A full arm-nonce handshake (the hub mints a per-boot nonce that a re-arm must echo, so a stale pre-reboot arm can never re-energise) is deferred — but the default is already safe (born disarmed), so adding the nonce later only tightens re-arming, never loosens it. Likewise an fw_id check that refuses arming on a mis-flashed board is deferred. These are real and worth doing; they are not needed to get communication and BB integration working, and each is a strict addition of a guard, consistent with the SAFeD rule in §00.

The actuator reports its own truth

An actuator hub writes a small status frame upward — {applied_seq, floored?} at minimum — so the host never has to infer whether a hub is driving. "Is this hub live?" is read from its reported status (gated by the same born-stale freshness check), never from "we sent it a command." That keeps the host from showing a confident green while a wheel sits floored. (A fuller fault/health fold across many hubs is SAFeD; v1 reports the one bit that matters.)

06The contract — generated, no drift

The router multiplies the number of codecs that must agree byte-for-byte — the Elixir host and every hub's C. The two ends that actually parse never meet a validator in the middle, so code generation is the only thing keeping them in sync. v1 generates the wire constants from one contract and drift-tests them; the fuller declare/pick/validate rail is deferred.

One model, one Elixir codec, four emitted artifacts

A hub's contract is authored in the BeamBots DSL, not a file that travels with it. A hub module declares each port's intrinsic wire facts — its dir, value-type, rate, t_dev, safe action, and pure sample/step core — and the robot's topology places that hub on a node id and wires its ports to BeamBots components, the consumer's fresh_for riding the view. A port names its value-type by module (§09); a value-type owns the layout (the ordered {field, wire_type} list), the host lift/unlift, and the firmware-hook signature for ports of its shape. A compile-time transformer projects the assembled DSL into one model (the IR), and from that model the host's Elixir codec is data-driven: it reads the resolved layouts at runtime rather than being generated into a file, so within Elixir it cannot diverge from the model — there is no generated .ex to fall stale. The drift risk lives only at the boundary the in-language guarantee can't reach — the other language — so the generator emits four artifacts and drift-tests them: the C header wire_contract.h (port ids, struct layouts, floor constants FLOOR_MISSES/CMD_PERIOD_MS, the contract hash); the per-hub glue header — the router table, hub_on_body, command dispatch, the floor init/on_command/control_tick/status plumbing, the schedule table (each port's rate as a {period_us, tick} row, §08), and hub_tasks — beside a companion <hub>.device.h declaring the hook prototypes the user owes; and the parity-vector fixture (§03). A drift test fails the build if any emitted file on disk differs from what the model would emit now, so the C constants physically cannot diverge from the Elixir definitions, and the parity vectors witness that the two codecs agree byte-for-byte. The next subsection sketches that generator.

The generator — contract → Elixir + C + glue + parity vectors

The generator is one small, pure pipeline run by mix compile (a file emitter for the C side). Its input is the assembled DSL: the hub modules' declared ports (intrinsic wire facts), the value-types they name (each carrying its resolved layout), and the topology that places each hub on a node id and wires its ports to components. A compile-time transformer projects that into one in-memory model (the IR); the generator renders the artifacts from it. The host's Elixir codec reads the model directly (data-driven, never emitted), and the generator emits four artifacts the other language and the wire test need, so nothing can describe different bytes or different rates — and the safety-critical seq/floor wiring is generated, not hand-glued per hub. There is no hand-written codec or hand-set period anywhere in the system; if you find yourself editing byte offsets or task periods by hand, that is the bug this section exists to remove.

The load-bearing idea is the value-type: a standalone module (use BBMCUHub.ValueType) whose layout is an ordered list of {field, wire-type}, and that layout — not the encoder code — is the source of truth both languages render. The library ships a lean stock set — imu, effort, status — and a consumer adds their own value-type in their own project with no library edit, since a value-type names no node, pin, or bot and so composes across hubs and robots. The encoder, the C struct, and the fixture bytes are all derived from the same layout, so a reordered field is a single-line change that ripples everywhere consistently; the value-type also owns the host lift/unlift (§09) and the firmware-hook signature for ports of its shape (§08), so one declaration governs both strata.

The compile-time checks v1 keeps

The full wire-budget and per-pick validation rail is SAFeD. v1 keeps the handful of checks that are cheap and catch a real bug on a laptop, run as a Spark verifier over the one projected model — so they fire at compile time. A malformed topology fails mix compile, raising a DslError that names the offending pair: the bug cannot ship, never mind reach the bus.

  • Topology is well-formed: every (hub, port) a reader names resolves to exactly one producer in the IR; a port read but never written, or written twice, fails to compile and names the offending pair.
  • Node ids are unique and the reserved low ids (host = 0, broadcast/e-stop = NODE 0x00) are not claimed by a data hub. This is a static check on the declared topology — it does not verify, on the live bus, that the board answering as a given NODE is the one you flashed (see the trust-on-first-use note below).
  • fresh_for ≥ one writer period: a window shorter than the producer's nominal period is refused — it could never be satisfied.
  • Floor window derives from one number: FLOOR_MISSES × CMD_PERIOD_MS is generated into the firmware from the same contract the host uses, so the host's view of the timeout and the hub's compiled-in timeout cannot drift apart.
  • Every value type's body fits the transport (§03): header + payload + CRC per type is checked against a single CAN FD frame (64 B) on a one-frame transport, or against the segmentation ceiling (64 fragments → 512 B) on classic CAN, so an oversized port is caught on a laptop, not refused or split-failing on the bus.
  • The parity-vector fixture passes (§03) — the codec/CRC witness.
node identity is trust-on-first-use in v1 the one blind spot, named not hidden SAFeD

The compile-time check above verifies the static topology — that the declared (node, port) map is well-formed and ids are unique on paper. Nothing on the live bus checks that the board answering as NODE 0x05 is the board you flashed as 0x05. With fw_id / board-identity deferred (§10, item 2), v1 trusts the NODE a frame claims: a mis-flashed, swapped, or duplicate board silently writes another hub's slot and is undetected until the fw_id check (2 bytes at the host decode seam, refusing arming on a mismatch) lands. This is consistent with the SAFeD rule — a confused board still cannot arm without a fresh in-window command its own floor witnessed (§05) — but it can corrupt a sensor slot a consumer reads, so it is a real gap. It is stated here rather than left implicit, because an unwritten assumption reads later as a guarantee that was never made.

The discipline in one line: the wire has one source of truth, the build proves the C and Elixir sides agree on it, and the few things that would silently corrupt a value or a command are checked on a laptop before any hardware moves. Everything richer than that is deferred, not pretended.

The host is not a hub — it sits above the tree and reaches every node through that one serial link to the root hub.

    do: {:no_command, law}        # no fresh angle ⇒ stop writing; the wheel's floor takes over

  def step(law, inputs, _stale, p) do
    %Pose{tilt: a, rate: r} = inputs.pose
    i = clamp(law.i + (p.setpoint - a) * p.ki, p.i_max)
    u = p.kp * (p.setpoint - a) + i + p.kd * -r
    {:emit, clamp(u, 1.0), %{law | i: i}}
  end
end

08Hub firmware — the per-port scheduler

Each port runs at its own rate (§04), so the firmware needs a way to drive many cadences from one loop without a hand-rolled timer per device. The answer is a tiny table-driven cooperative scheduler: each port becomes a {period, tick} row in the per-hub glue generated from the contract, and one loop fires each row when its period has elapsed. The user writes only the thin firmware hook for each port — a bounded device read or drive; the schedule table, the floor and command wiring, the framing, and the routing are all generated glue.

The scheduler — one table, many rates

Every job on a hub is a period plus a tick function. The IMU's pose port at 50 Hz is a row with period_us = 20 000; a range port at 20 Hz is 50 000; the actuator floor runs every loop (period 0). The loop checks each row's elapsed time and calls the ones that are due — cooperative, non-preemptive, no per-device timer, no RTOS task. Because the rows are generated into this hub's glue header from its contract, a hub only contains the tasks its ports declare: a sense-only leaf has no control_tick, a pure actuator has no sample task. The generated tick wraps the user's device hook (it calls imu_read, drains the floor, advances the seq); the user never wires a task into the table by hand. The same source that sizes the wire (§06) sizes the schedule, so a port's declared rate and its firmware period can never disagree.

Cfirmware/src/scheduler.cperiod + tick, one loop drives them all 
/* The chassis loop is hub-agnostic; the task table is GENERATED into this hub's
   glue header — only the ports this hub actually has appear there. One loop fires
   each task when due; nothing preempts, so every tick must be bounded.       */
typedef struct { uint32_t period_us, last_us; void (*tick)(uint32_t now); } Task;

/* --- generated: firmware/gen/<slug>/<this hub>.glue.h provides hub_tasks[] --- */
static Task hub_tasks[] = {
  {  20000, 0, pose_sample_tick   },   /* SENSE pose @ 50 Hz — wraps imu_read hook  */
  {  50000, 0, range_sample_tick  },   /* SENSE range @ 20 Hz                       */
  {  20000, 0, status_write_tick  },   /* report status @ 50 Hz                     */
  {      0, 0, control_tick       },   /* ACT: floor + drive — every loop (kHz)     */
};

void loop() {
  uint32_t now = micros();
  feed_watchdog();                              /* hardware backstop, independent of any tick */

  for (size_t i = 0; i < N_HUB_TASKS; i++) {     /* fire every task that is due */
    if ((uint32_t)(now - hub_tasks[i].last_us) >= hub_tasks[i].period_us) {
      hub_tasks[i].last_us = now;                /* schedule next; tick gets `now` so it needs no clock of its own */
      hub_tasks[i].tick(now);
    }
  }

  link_pump_up();    /* drain the link toward the host (UART on the root hub; CAN on a deeper hub) */
  link_pump_down();  /* ROUTE (§04): strict FIFO byte pump — move frames between links in ARRIVAL
                        order, meaning-blind, seq/t_dev verbatim. No reorder/hold/dedup: this in-order
                        guarantee is what makes the floor's seq!=last_seq test sound (§05). */
}
three properties the table buys, for free
Mixed rates, no interference

A 50 Hz and a 20 Hz port are just two rows with different periods. Adding a sensor is adding a row; its cadence is independent of every other.

The floor is never starved

control_tick has period 0, so it runs every loop pass regardless of how many sensors are due — the dead-man's cadence is not at the mercy of telemetry.

Generated, so it can't drift

The periods come from the same contract as the wire codec and the host's rate picks (§06), so "50 Hz" means one number in three places, checked by the drift test.

the one rule that makes cooperative scheduling safe every tick is bounded

Cooperative means one slow tick delays every other — a blocking I²C read would push the floor's next pass late. So every tick must be bounded by construction: device reads use a timeout (Wire.setTimeOut), a tick never spins or waits, and a tick that cannot complete simply returns and writes nothing (its seq stalls, the reader goes stale — the failure is legible, not a hang). A hardware watchdog, fed at the top of the loop and never from inside a tick, is the backstop: if any tick wedges the loop past the watchdog window, the chip resets and the actuator comes up born-disarmed (§05). This is why the floor's safety does not actually depend on the scheduler being timely — a late or dead scheduler resolves to command-silence, which is exactly what the floor already handles.

The watchdog guards the loop, not bring-up. The task subscribes to the watchdog after hub_setup() returns — never before. A device's one-time bring-up (<hub>_device_setup()) is allowed to take as long as it needs: a SimpleFOC initFOC() sensor-alignment spins the motor for seconds, an i2c-ng bus needs a settle delay, a sensor wants a calibration pass. Watchdogging setup would reset the chip mid-alignment, before the loop can ever feed the timer — a boot loop that never finishes initialising (the recognisable symptom: the ROM banner repeating with task_wdt … did not reset … Rebooting). So the bound applies to ticks; bring-up is deliberately outside it. A consumer writing a slow _device_setup needs no watchdog ceremony — the chassis already orders it correctly.

}

void pose_sample_tick(uint32_t now) {
  Imu raw;

  Frame f = { .node = MY_NODE, .port = PORT_POSE,
              .seq = pose_seq++, .t_dev = now, .payload = c.value };   /* `now` = this hub's own µs */

}
Cfirmware/mcu/imu.cthe hand-authored device hook — all the user owes 
/* HAND-AUTHORED. The ONLY firmware the user writes for this hub: device setup
   plus, per port, a bounded read/drive hook. The hook's SIGNATURE is owned by
   the port's value-type (imu) and declared in the generated imu.device.h, so
   the contract the user owes is legible and resolved at link time.            */
bool imu_pose_read(Imu *out) {
  return bno055_read(out);                  /* bounded by Wire.setTimeOut; false → tick writes nothing */
}
void imu_device_setup(void) { bno055_begin(); }   /* init pins/peripherals */

The split is the whole point: the scheduler owns when (the chassis loop), the generated tick owns the wiring (one row per port, the floor and command plumbing, the seq advance), the hand-authored hook owns one bounded device step, and the pure sample owns the math — four concerns, four homes, none of them a timer or a frame the user has to write. Everything under gen/ is generated and drift-tested; everything under mcu/ is hand-authored. A faster or slower port is a different number in the contract; the hook and the sample never change, and a user-defined hub is wired identically to a stock one.

The sensor view — read a slot, witness a write, publish

A hub port surfaces as a component by being named in the topology: the hubs do block places the hub module on a node id (§06) and a sensor view names the hub: and port: it reads, carrying its own fresh_for. That view is a BBHub.Sensor — a beat loop and almost nothing else. The link owner has already decoded inbound frames into the (node, port) registry row; the view's whole job is to pull that row on its own beat, ask the born-stale monitor "did seq advance?", and lift a fresh value into a typed BB.Message on BeamBots' PubSub. It holds no socket, names no transport, and cannot tell whether the value came from the root hub's own I²C or a leaf three CAN hops down.

defmodule BBHub.Sensor do
  use BB.Sensor,                      # a CALLBACK module; BB.Sensor.Server wraps it
    options_schema: [                       # validated before init; :bb is auto-injected
      hub: [type: :atom, required: true], port: [type: :atom, required: true],
      fresh_for: [type: :pos_integer, default: 3],
      beat_ms: [type: :pos_integer, default: 20]]
  # A thin VIEW over a slot the link owner fills: slot + monitor + publish. Born
  # stale — nothing is published until it witnesses seq advance since ITS boot.

  @impl true
  def init(opts) do
    bb = opts[:bb]                                        # %{robot:, path:} — auto-injected
    {:ok, {node, port}} = PortIndex.resolve(opts[:hub], opts[:port])  # hub+port → wire (NODE, PORT)
    :timer.send_interval(opts[:beat_ms], :beat)           # the view's OWN beat (no built-in poll)
    {:ok, %{bb: bb, node: node, port: port, type: PortIndex.type!(node, port),
            mon: Monitor.new(node, port, opts[:fresh_for])}}   # witnessed: false → born stale
  end

  # Each beat: update the freshness monitor, publish only if fresh. The view is
  # VALUE-TYPE-AGNOSTIC: it delegates lifting to the port's value-type module, so a
  # consumer's own value-type surfaces through this same view unchanged.
  @impl true
  def handle_info(:beat, st) do
    mon = Monitor.check(st.mon)                       # did seq advance within fresh_for? (§04)
    if Monitor.fresh?(mon) do
      {value, _seq, _t} = NodeRegistry.get(st.node, st.port)
      BB.publish(st.bb.robot, [:sensor | st.bb.path], st.type.lift(value))  # value-type owns the lift (§06)
    end                                                  # stale → publish NOTHING
    {:noreply, %{st | mon: mon}}
  end
end

The actuator view — decode a command, write its one slot

A BBHub.Actuator is the mirror image, and it is the single writer of its outbound command slot — the link owner only ever drains that slot to the wire, never writes it (so the link owner can never manufacture a seq advance, §04). The single-writer rule is enforced structurally: the view mints a slot-scoped Registry.Writer capability at init and writes through it (ADR-0007, the write-side mirror of the observer Reader), so a second view on the same slot fails loud at init (Writer.Taken) rather than silently sharing it. After each write the view casts notify_command_slot to the link owner, so the drain is event-driven (no poll). The actuator server auto-subscribes the command topic — for the command struct the port's value-type names (command_message), so a consumer's own command value-type flows through unchanged, the view never naming a struct — and delivers each command to handle_info; the view decodes the BB.Message and puts the command slot, advancing the command seq once per command. The hub's own floor (§05) does the safety work; the view never drives hardware directly. Liveness is read from the status slot through a born-stale monitor, so a stale "not floored" never reads as driving.

defmodule BBHub.Actuator do
  use BB.Actuator,                          # callback module; BB.Actuator.Server wraps it
    options_schema: [
      hub: [type: :atom, required: true], port: [type: :atom, required: true],
      status_port: [type: :atom, required: true],
      fresh_for: [type: :pos_integer, default: 5],     # the command window the IR carries to the floor (§04/§05)
      status_fresh_for: [type: :pos_integer, default: 5],
      beat_ms: [type: :pos_integer, default: 20]]
  # SOLE writer of its command slot; the link owner is a read-only drain. Owns no
  # socket. The on-chip floor is the safe-state mechanism — this view relays intent
  # and reads truth back from the status slot (through a born-stale monitor).

  @impl true
  def init(opts) do
    bb = opts[:bb]                                         # auto-injected; the server auto-subscribes commands
    {:ok, {node, cmd}}    = PortIndex.resolve(opts[:hub], opts[:port])    # hub+port → wire (NODE, PORT)
    {:ok, {^node, status}} = PortIndex.resolve(opts[:hub], opts[:status_port])
    :timer.send_interval(opts[:beat_ms], :status_beat)     # tick the status freshness monitor
    {:ok, %{bb: bb, node: node, cmd: cmd, status: status, seq: 1,
            type: PortIndex.type!(node, cmd),               # the command port's value-type module
            status_mon: Monitor.new(node, status, opts[:status_fresh_for])}}
  end

  # A command from BeamBots → write our ONE command slot (single-writer; each put
  # advances the command seq). The link owner drains it; the floor decides to act.
  # VALUE-TYPE-AGNOSTIC: the port's value-type owns unlift, so any value-type fits.
  @impl true
  def handle_info({:bb, _topic, %BB.Message{} = msg}, st) do
    NodeRegistry.put(st.node, st.cmd, st.type.unlift(msg), st.seq, 0)  # value-type owns the unlift (§06)
    {:noreply, %{st | seq: st.seq + 1}}
  end
  def handle_info(:status_beat, st), do: {:noreply, %{st | status_mon: Monitor.check(st.status_mon)}}

  # "Is it driving?" is read from the STATUS slot, GATED by born-stale freshness:
  # a stale (or never-witnessed) status reads floored/unknown, never driving (§05).
  def live(st) do
    if Monitor.fresh?(st.status_mon) do
      case NodeRegistry.get(st.node, st.status) do
        {%{floored: false}, _, _} -> :driving
        _ -> :floored_or_unknown
      end
    else: :floored_or_unknown
  end

  # disarm/1 is BEST-EFFORT and runs WITHOUT GenServer state (opts only). Return
  # means "intent delivered," NOT "the hardware is safe" — that is the floor's.
  @impl true
  def disarm(_opts) do
    LinkOwner.send_disarm()                               # broadcast accelerator; the floor backstops
    :ok
  end

what these two modules deliberately are not

Neither view opens a port, frames a byte, or names UART vs CAN — all of that is the link owner's, so the views are pure lift + a freshness gate and would run unchanged if a port moved from the root hub's I²C to a CAN leaf. Neither view makes anything safe: the sensor stops publishing when stale, the actuator relays intent and reads truth back through a born-stale monitor, and the hub's own floor is the safe-state mechanism. And the actuator is the only writer of its command slot — the rule that lets the link owner be a harmless read-only drain (§04), and one now enforced structurally by a per-slot Registry.Writer capability (ADR-0007), not just by convention. Because the actuator server auto-subscribes the command topic and auto-registers the actuator for disarm when disarm/1 is implemented, the view's only standing obligation is to implement the callbacks correctly — there is no manual subscribe/register to forget.

On the outbound drain, a command value the link owner cannot pack to the wire (a malformed value-type value — e.g. a map missing a layout field) is counted as encode_fail and skipped, never crashing the drain (which would take down telemetry and every other slot). The floor backstops the unsent command via silence, but the cause stays legible as a counter — the same fail-into-legibility discipline as the inbound drop counters (rx_drop, crc_fail, cobs_truncated, decode_fail).

The views are deliberately thin: lifting already lives in the port's value-type (lift/unlift), so the same two modules serve every value-type — stock or consumer-defined — without a per-atom clause. Generating the views themselves from the contract (so options_schema is the contract and init self-subscribes and registers automatically) is SAFeD. v1 hand-writes these two small modules to get the BeamBots round-trip working, holding to the rules above: value-type-agnostic lift, born-stale, single-writer, no socket.

Two planes over the slots — control and observability

Everything above is the control plane: the views, the controllers and laws, the command path, the floor — all acting on the robot's truth at control rate. Watching that truth — a dashboard, a disk log, an event database — is a separate observability plane. The two share the host's (node, port) registry slots and nothing else. The reason to keep them apart is concrete: the loop may run at 100 Hz, but a human dashboard wants ~10 Hz and a logger may want full fidelity — each consumer must pick its own rate, and none may slow the loop or each other.

An observer is the observability plane's consumer: a host-side pure reader that samples a slot directly from the registry at its own cadence and hands the result to a pluggable sink. It does not ride the control-plane PubSub. Because the slot is overwrite-only and reads return the latest, an observer pulling the latest at its own timer is structurally unable to apply backpressure to or slow the producer — N observers are N independent readers, and adding one costs the others nothing. Each observer carries its own born-stale monitor per slot, so fresh_for is relative to its beats and it never reports a leftover value.

two modes — two different mechanisms, not one reader
sample-state (level) — v1

A pure registry poll: read the slot's latest value on your own timer; dropping the values skipped between polls is correct (overwrite-only-latest). For "what is it now?" — a UI monitor of pose, status, effort. This is the registry-direct pure reader, and it is all of v1.

stream-events (edge) — deferred

Must catch every advance — which a poller cannot: between polls seq can jump 1→5 and the overwrite-only slot has discarded 2–4 (Advance, §04, guarantees the producer emits every edge, not that a sampler sees them). So it is not registry-sampling — it taps the LinkOwner's unconditional decode fan-out (the one place every decoded advance lands). For every command / floor-fired / arm-disarm; an event DB or log that must not miss one. SAFeD.

An observer is a declarative reduction of the firehose to just what it needs, along four axes: sample (rate decimation; state mode), select (which slots / which edges), filter (a value/event predicate), and project (which fields). v1 implements sample + select; filter and project are extensions of the same shape (designed, not yet built) — and because they act on a value's fields, which only the value-type knows, they resolve the slot's value-type (via PortIndex + BBMCUHub.ValueType, exactly as a view does), never duplicating field knowledge. The observer's one job is sample → reduce → hand to a sink; what to do with the value/event lives in the sink — a PubSub republish on the observer's own slow topic, a disk log, an event database, a UI feed are all just sinks (the sink runs in the observer's own process, so a slow sink degrades only that observer, never the loop).

an observer's freshness is not the control plane's

fresh_for is relative to the observer's own (slower) beats, so a 10 Hz observer can report :fresh for a slot the 100 Hz loop already floored — correct for "is what I'm showing recent," but for "is the hub actually driving" read the authoritative status slot (floored?, §05), never an observer's own freshness verdict.

an observer is a PURE READER the invariant that keeps the concept clean

An observer never writes a slot, never issues a command, and nothing in the control plane may depend on an observer existing. This is enforced structurally, not by convention: an observer is handed a read-only registry capability (only get/dump; put not in scope), so "an observer writes a slot" is unrepresentable — the registry is :public ETS, so the "one writer per slot" rule is otherwise just a comment. This is what makes observability purely additive — a new observer touches no producer, view, controller, or other observer — and the isolation is from backpressure (a direct :ets.lookup on a read-concurrent table cannot block a producer), not from CPU: many fast observers still share the BEAM scheduler. An observer is also not part of the wire contract: pure host runtime, no firmware, no generated artifact, drift-neutral, so it is added or removed without regenerating anything. An observer that writes — or that the loop depends on — is a control-plane actor in disguise, and is forbidden.

Running a robot virtually — simulate at the transport

The whole host stack runs without hardware by swapping the one thing that is the hardware boundary — the transport the LinkOwner owns (§07). Above that seam everything is the real robot: the codec, the freshness monitor, the floor's meaning, the views, the dashboard. Below it sits the wire, the hubs, the silicon, and the physical plant. So to run a robot virtually, you replace nothing above the seam and simulate at it — a third transport beside the production UART and the in-process test loopback. Only the transport ever knows whether the robot is real (ADR-0008).

The library ships three engine-agnostic pieces. A sim transport (BBMCUHub.Sim.Transport) implements the Host.Transport behaviour and, on each outbound send/2, captures the newest command per (node, port) slot — a pure capture, no clock. A plant (BBMCUHub.Sim.Plant, a behaviour) is the consumer-supplied dynamics: given the latest per-slot commands and a dt, it advances a simulated world and returns the sensor values the hubs would have produced — spoken in value-type values keyed by wire slot, never robot structs, the same byte-/value-generic stance as a safe action (ADR-0005). A driver (BBMCUHub.Sim.Driver) is the real-time loop: a sibling process owning a ~50 Hz clock that reads the captured commands, calls Plant.step, and injects each returned sensor back up as a wire body via Codec.encode_body — delivered to the LinkOwner exactly as the UART driver delivers a decoded frame, so the sensor view witnesses a fresh seq advance and born-stale is honored unchanged. The loop lives in the driver, not the transport, so a plant crash restarts the loop without tearing down the link.

The split follows ADR-0003: the library ships the building blocks; the consumer writes the plant. The worked example's plant (SegbyV1.Sim.MujocoPlant) drives a headless MuJoCo physics engine over a Port to a small Python child, whose native launch_passive viewer renders the bot in 3D beside the terminal dashboard while an operator teleops it — the real balance loop, floor, and wire path all in the middle. The library itself carries no physics engine and no Python; a different consumer writes a different plant (a pure-Elixir toy pendulum, a recorded-trace replay, another engine) against the same behaviour. This narrows the sim-to-real gap — control logic (balance gains, teleop mixing, the pitch→wheel sign) is developed and de-risked against faithful dynamics before a board is powered — but it does not replace the bench's silicon truths (motor/encoder sign, pin map, FOC alignment), since the sim runs with whatever sign you modeled. It is also distinct from the deterministic, frozen-clock, real-C-floor test seam used for assertions: same philosophy — simulate at the transport — but this one is the interactive, real-clock, physics-backed development surface. SAFeD The sim transport, plant behaviour, and driver are specified here and in ADR-0008; v1 builds them as a new library seam plus the example's MuJoCo plant.

SAFeD the deferred list, in priority order

Each item below is a strict addition of a guard or a capability — none changes a v1 default away from safe. Build order is roughly top to bottom, but v1 ships and integrates with BeamBots before any of these:

  1. Arm-nonce handshake — a per-boot nonce a re-arm must echo, so a stale pre-reboot arm cannot re-energise. Tightens the born-disarmed floor.
  2. fw_id / board-identity — 2 bytes per hub, checked at the host decode seam; a mis-flashed or swapped board is refused arming. Closes v1's trust-on-first-use gap (§06): until it lands, the NODE a frame claims is believed without verifying the physical board.
  3. Conflation / backpressure — one pending value per (node, port), newest wins, seq advances only on a real change; bounds bursty push traffic and reconnect backlogs.
  4. Per-register params + EEPROM/SRAM split — runtime tuning of gains, clamped against declared [min,max] host-side and at the hub.
  5. Wire-budget & full declare/pick/validate — refuse a topology that over-subscribes a link; one rail for every pick.
  6. Host coordination policy — cross-hub judgment (a dangerous combination no single hub floored on) that may initiate a stop; pure decide/3 + thin shell.
  7. A registerable HubDevice vtable (Shape 2) — a struct of function pointers the device file fills, for runtime device-swap and host-mocked hubs. The generated glue (§08) resolves hooks by well-known link-time names (Shape 1) and does not preclude adding this later.
  8. Health fold across scopes, self-heal, and A/B firmware. (A branch hub bridging to a deeper sub-bus below a limb is already part of the model — every hub reaches its children over declared links, and the route table maps each node to the specific link — so a multi-hop tree is first-class, not a future generalisation.)

The whole of v1 in one sentence: one recursive hub that senses, acts, and routes; a correct CRC-checked frame carrying a producer-owned seq; a floor on each actuator's own chip that is safe by default and earns motion; and a generated contract that keeps the C and Elixir wire from ever drifting — enough to bring a tree of microcontrollers into BeamBots, and a safe foundation to elaborate.
